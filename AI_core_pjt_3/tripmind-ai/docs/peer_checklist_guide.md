# TripMind AI 상호 체크리스트 작성 가이드

대상은 TripMind AI를 처음 보는 교차 평가자다. 앱을 한 번 실행한 뒤 화면과 테스트 결과를 확인하고, 받은 체크리스트의 **결과**, **증빙**, **비고** 칸에 관찰한 내용을 적는다. 개발자가 남긴 증빙은 직접 확인한 결과와 구분해 기록한다.

## 1. 서비스 이해

TripMind AI는 국내 목적지의 관광지를 추천하고 일정을 만드는 서비스다. TourAPI에서 관광지, Open-Meteo에서 날씨 예보, 에어코리아에서 현재 대기질 관측값을 조회한다. 일정은 날짜별로 저장할 수 있고, 실행 로그에서는 실제로 실행된 단계와 Tool 호출을 확인할 수 있다.

- **여행 대화**에서 질문하고 답변·출처·실행 과정을 확인한다.
- **저장한 계획**에서 일정의 조회·수정·삭제와 화면 반영을 확인한다.
- **실행 로그**에서 세션별 요청 처리 과정을 확인한다.
- **Swagger**는 각 API에 요청해 JSON 응답과 HTTP 상태를 확인하는 화면이다.

## 2. 실행 준비

프로젝트를 받은 폴더에서 Git Bash를 연다. 이미 가상환경이 있으면 첫 줄을 건너뛴다. 8000번 포트의 기존 서비스와 혼동하지 않도록 검증용 서버는 8001번 포트를 사용한다.

```bash
python -m venv .venv
source .venv/Scripts/activate
python -m pip install -r backend/requirements.txt
QA_DIR=$(mktemp -d)
export TRIPMIND_DB_PATH="$(cygpath -m "$QA_DIR")/peer-check.sqlite3"
python -m uvicorn backend.main:app --port 8001
```

[평가용 화면](http://127.0.0.1:8001/)을 열고 [상태 확인](http://127.0.0.1:8001/health)에 `{"status":"ok"}`가 표시되는지 본다. 이어 [Swagger](http://127.0.0.1:8001/docs)를 열어 둔다. 검증용 SQLite는 별도 경로에 생성되므로 아래 삭제 시험은 이 서버에서 만든 테스트 데이터에만 수행한다.

실연동을 확인하려면 평가 환경에 사용할 수 있는 GMS, TourAPI, 에어코리아 설정이 필요하다. 이미 실행 중인 평가용 앱을 제공받았다면 전달받은 주소에서 화면 검사를 수행한다. 키가 없는 경우에도 아래 로컬 테스트와 기존 증빙을 검토할 수 있다. GMS 키가 없는 상태에서 자연어 일정 생성은 실연동 미확인으로 적는다. 키 값이나 `.env`는 공유하거나 캡처하지 않는다.

### 터미널 확인

서버를 실행한 터미널과 별도로 Git Bash를 하나 더 연다. 프로젝트 루트에서 아래 명령을 실행한다.

```bash
source .venv/Scripts/activate
python -m unittest backend.tests.test_service backend.tests.test_external_apis.LocalToolTests backend.tests.test_llm.LlmRoutingTests -v
python -m backend.tools.registry
python -c "from backend.agents.graph import graph; print(graph.get_graph().draw_mermaid())"
```

실연동 설정이 준비된 환경에서는 아래 명령도 실행한다.

```bash
python -m unittest backend.tests.test_external_apis.ExternalApiTests backend.tests.test_llm.LlmTests -v
```

각 항목의 `ok`는 성공, `FAIL`은 실패, `skipped`는 미확인이다. 마지막 줄이 `OK`여도 개별 테스트에 `skipped`가 있으면 그 호출은 미확인으로 적는다.

## 3. 화면에서 따라 할 테스트

날씨를 함께 보려면 입력 예시의 날짜를 **오늘 이후 예보 범위 안에 있는 날짜**로 바꾼다. 새 테스트를 시작할 때는 **새 대화**를 누르고, 이전 조건을 이어받는 테스트에서만 같은 대화를 사용한다.

### A. 여러 날 일정과 출처

다음 요청을 보낸다.

> 11월 21일부터 24일까지 부산 여행 일정을 짜 줘. 매일 오전 10시부터 오후 5시까지 하루 두 곳씩 실내와 야외를 섞어 줘. 각 장소에서 최소 30분 머물고 싶어.

1. 전송 직후 처리 중 표시를 확인한다.
2. 응답에 1~4일차가 표시되는지 본다. 확인된 후보가 충분하면 매일 실내와 야외가 함께 나온다. 부족한 날은 안내 문구를 확인한다.
3. 하루 420분에서 최소 체류 60분을 뺀 **360분**이 이동 등 여유 시간으로 안내되는지 본다. 확인되지 않은 실제 이동시간과 운영시간은 확인이 필요한 값으로 표시돼야 한다.
4. **출처**에 TourAPI·Open-Meteo·AirKorea의 성공한 조회 결과가 표시되는지 확인한다. 에어코리아는 측정소와 측정 시각이 표시된 현재 관측값이다.
5. 같은 대화에서 `종료 시간만 오후 6시로 바꿔 줘`를 보내고 다른 조건이 유지되는지 확인한다.

### B. 조건 부족과 Tool 없는 대화

1. 새 대화에서 `이번에 부산 여행 일정을 짜 줘`를 보낸다. 날짜·시각·장소 수를 확인하는 질문이 나오는지 본다.
2. 다시 새 대화를 열어 `안녕하세요`를 보낸다. 대화 응답이 나오고 **실행 과정**에 외부 Tool 호출이 없는지 본다.

### C. 저장과 중복·수정·삭제

1. A에서 날짜별 **일정 저장** 버튼으로 하루를 저장한다. **저장한 계획** 탭에 해당 날짜의 계획이 표시되는지 확인한다.
2. 같은 날짜와 겹치는 시간대로 다시 일정을 생성해 별도 계획으로 저장한다. 저장 성공과 충돌 안내가 함께 표시되는지 확인한다.
3. 테스트 계획 제목을 수정해 목록 이름이 바뀌는지 본다. 해당 테스트 계획을 삭제해 목록에서 사라지는지 확인한다.

### D. 로그 확인

1. **실행 로그** 탭에 A와 B의 세션이 각각 표시되는지 본다.
2. 브라우저 **F12 → Network → Fetch/XHR**를 열고 새 요청을 보낸다. `chat` 응답의 `session_id`, `run_id`, `events`를 찾는다.
3. Swagger에서 `GET /api/logs/{session_id}`의 **Try it out**을 눌러 같은 세션 ID를 넣고 실행한다. 같은 `run_id`에서 `event_id`, `seq`, `payload`가 일치하는지 본다.
4. 테스트 세션을 `DELETE /api/logs/{session_id}`로 삭제한다. 상태 `204`와 같은 세션 재조회 시 `404`를 확인한다.

## 4. 체크리스트 번호별 판정 기준

각 항목에 해당하는 확인을 수행한 후 **결과, 증빙, 비고**를 작성한다. 테스트 이름과 로그 필드를 찾기 어렵다면 [항목별 상세 가이드](checklist_guide.md)에서 같은 번호를 찾는다.

모든 확인 조건이 충족되면 **통과**, 일부만 확인했으면 **부분 확인**, 실행했지만 기대와 다르면 **실패**, 실행하거나 증빙을 확인할 수 없으면 **미확인**, 도메인이나 설정상 적용 대상이 아니면 **해당 없음**으로 표시한다. 증빙 칸에는 실제 첨부한 파일명을 적고, 비고에는 직접 실행·재현·기존 증빙 검토 중 어디까지 했는지 남긴다.

### Tool · 1~4번

- **1 · F3001** — Tool 목록 출력과 [Tool 정의서](tool_spec.md)의 이름·설명·입력 스키마를 대조한다. 정상 호출 출력과 유효하지 않은 입력·키 누락 응답을 확인한다. Open-Meteo는 키 누락 시험이 해당 없음이다. 잘못된 입력과 키 누락을 재현하는 명령은 [상세 가이드](checklist_guide.md#1--f3001-tool-등록과-정상실패-응답)에 있다. 증빙은 목록과 정상·실패 출력이다.
- **2 · F3002** — 날짜 생략과 미래 날짜 지정 결과의 `requested_date`, `checked_at`, `basis`를 비교한다. 앱 답변에 관광지가 현재 카탈로그 기준임을 밝히는지 확인한다. 증빙은 두 호출 출력과 답변 화면이다.
- **3 · F3002·F3003** — 검색 결과의 후보 ID가 상세 요청에 전달됐는지 로그에서 대조한다. 속성 결측은 실제 사례 또는 재현 테스트로 확인하고 방식을 비고에 표시한다. 증빙은 후보 ID와 상세 입력값이다.
- **4 · F3004** — `부산의 현재 대기질을 알려 줘`로 측정소·시각·관측값·출처를 확인한다. 빈 결과는 `ok: false`와 `error.code`를 확인한다. 증빙은 관측 화면과 빈 결과 출력이다.

### 메인 Agent · 5~13번

- **5 · F3005** — A와 B에서 `conditions_extracted`를 비교한다. 빠진 조건을 채워 넣지 않고 질문하는지 확인한다. 증빙은 정상·누락 요청의 조건 JSON이다.
- **6 · F3006** — `plan_created`, `tool_requested`, 인사 요청에서 Tool 0회, 터미널의 그래프 노드 출력을 확인한다. 증빙은 실행 과정과 그래프 출력이다.
- **7 · F3007·NF3003** — 후보 ID 전달을 대조한다. `test_weather_failure_returns_tourism_and_warning`에서 날씨 실패에도 관광지 답변이 반환되는지 보고, 이어 별도 정상 요청을 실행한다. 증빙은 실패 재현과 다음 정상 응답이다.
- **8 · F3008** — A의 420분, 최소 체류 60분, 최대 여유 360분을 대조한다. 실제 이동시간과 운영시간이 확인 필요로 표시되는지 본다. 증빙은 답변의 계산 문구다.
- **9 · F3009** — 재계획 재현 로그의 `replanned`와 날씨 요청 횟수를 본다. 새 검색이 추가되고 이미 조회한 예보 호출이 반복되지 않는지 확인한다. 증빙은 `rain-replan` 로그다.
- **10 · F3009·NF3004** — `cap` 재현 로그에서 재계획 카운트 1·2·3과 `run_finished`, 답변의 상한 안내를 확인한다. 증빙은 이벤트와 종료 응답이다.
- **11 · F3010** — A의 후속 요청에서 바뀐 종료 시간과 그대로인 조건을 비교한다. 증빙은 같은 세션의 변경 전·후 `conditions_extracted`다.
- **12 · F3011** — `부산에서 실내 관광지만 3곳 추천해 줘`로 추천·판단 기준·출처와 제외 사유를 확인한다. 제외 사례가 없으면 해당 조건을 미확인으로 적거나 다른 요청으로 재확인한다. 증빙은 제외 사유가 포함된 답변 화면이다.
- **13 · F3011** — 위험 도메인 안내는 **해당 없음**으로 적는다. 비고는 “국내 여행 일정 추천 도메인”으로 작성한다.

### 로깅과 계획 관리 · 14~20번

- **14 · F3012·F3013** — D에서 세션 분리를 확인한다. `node_enter`, `node_exit`, `tool_requested`, `tool_completed.duration_ms`, `llm_decision.intent`와 `reason`을 본다. 증빙은 세션 두 건과 해당 이벤트다.
- **15 · F3012** — `test_no_tool_log_isolation_and_subscriber_failure`의 `subscribers=()` 실행을 확인한다. 증빙은 테스트 위치와 통과 출력이다.
- **16 · F3013** — [로깅 Agent](../backend/agents/logger.py)가 이벤트를 저장 함수에 전달하는 코드를 확인한다. 증빙은 저장 코드와 정상 실행 로그다.
- **17 · F3013** — D에서 대화 응답과 저장 이벤트를 비교한다. 같은 서비스 테스트에서 로깅 구독자 실패 시에도 응답이 유지되는지 확인한다. 증빙은 JSON 비교와 테스트 출력이다.
- **18 · F3014** — D의 로그 목록·상세·삭제를 수행하고 Swagger에서 로그 수정 메서드가 없는지 확인한다. 증빙은 목록·상세와 삭제 전후 응답이다.
- **19 · F3015** — C에서 저장과 중복 안내를 확인한다. Swagger 상세의 `created_at`과 중복 저장 응답의 `201`, `conflicts`를 확인한다. 증빙은 상세와 중복 저장 응답이다.
- **20 · F3016** — C의 제목 수정과 삭제 후 목록 갱신을 직접 확인한다. 증빙은 수정 후 화면과 삭제 전후 화면이다.

### 화면과 제출 · 21~27번

- **21 · F3017·F3018** — Swagger를 [API 명세](api_spec.md)와 대조한다. 브라우저 Network에서 대화의 `POST /api/chat`과 계획 화면의 `GET /api/plans`를 확인한다. 증빙은 Swagger와 두 네트워크 요청이다.
- **22 · F3019** — A에서 처리 중과 실행 순서를 직접 보고, 기존 재현 화면에서 재계획·Tool 실패·키 누락 표시를 확인할 수 있다. 증빙은 현재 처리 중 화면과 재현 화면이며, 어느 버전인지 비고에 남긴다.
- **23 · 필수·NF3005** — [대표 시나리오 기록](evidence/scenario-runs.json)의 정상·재계획·상한·실패·Tool 불필요 다섯 유형을 확인한다. 각각 `reply`, Tool 순서, 재계획 수, 기대와 실제 차이, `run_finished.payload.duration_ms`를 기록한다. 현재 앱의 실연동 시간은 A에서 얻은 값으로 추가한다.
- **24 · 필수** — [대표 실제 실행 로그](evidence/normal-live.json)와 [재계획 사례](evidence/scenario-runs.json)를 열어 실제 정상 요청 한 건의 전체 이벤트와 재계획 사례가 첨부됐는지 확인한다. 파일명을 증빙 칸에 적는다.
- **25 · NF3001·NF3002** — 평가용 제출 묶음에 `.env`나 비공개 DB가 없는지 확인한다. 실패 화면에서 원본 오류와 키가 표시되지 않는지 본다. 실제 키 대조 권한이 없으면 그 부분은 미확인으로 적는다.
- **26 · NF3006·NF3007** — `frontend/`, `backend/agents/`, `backend/tools/` 분리와 [외부 API 이용 조건](api_verification.md#출처-필수-인자와-이용-조건)을 확인한다. 증빙은 파일 구조와 이용 조건 문서다.
- **27 · 필수** — [검증 문서](verification.md)와 최종 제출 묶음을 대조한다. 요구사항·Agent·Tool·API 문서, 소스, README, 현재 화면 캡처, 실행 로그, 작성한 체크리스트가 있는지 확인한다. 심화 기능은 미선택이다. 1일차 16시 조건과 이후 API 성공 기록은 [API 검증 기록](api_verification.md)에서 구분해 확인한다.
