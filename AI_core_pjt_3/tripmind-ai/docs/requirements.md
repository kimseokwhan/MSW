# 1일차 요구사항과 도메인 기획

기준은 같은 폴더의 공식 프로젝트 명세서 1~30쪽이다. 명세서의 필수 요구사항은 아래 표의 '공식 요구' 열에 요약했다. 여행 도메인 적용, 파일 배치, 시나리오와 검증 절차는 **프로젝트 자체 설계**다.

## 공식 목표와 1일차 검증

- 사용자 조건을 분석해 외부 Tool을 선택하고, 확보한 데이터로 제약을 계산하며, 필요한 경우 재계획한다. 세션 맥락을 유지하고 별도 로깅 Agent로 실행 과정을 기록한다. 계획과 로그를 저장하며 FastAPI 백엔드와 화면을 분리한다.
- 도메인은 서로 다른 정보를 주는 외부 API 최소 3종, 비교 판단과 재계획이 필요한 요청, CRUD로 관리할 결과물이 있어야 한다. 1일차 16시까지 코드 호출을 확인한다. 미통과 시 명세서 §1.2·§2.7에 따라 제공 영화 도메인 팩으로 전환한다.
- §2.1~2.7은 도메인과 이용 조건 확정 → 대표 요청 및 조건 → Tool 계약과 인자 전달 → Agent 상태, 판단식 및 재계획 → 이벤트, 저장 및 API → 요구사항 표 → 기획 실증 순이다. 이번 작업은 마감 관련 API 검증을 먼저 시도했다.
- 기획 통과 증거는 API별 유효 응답과 Tool 필드 대조, 누락·빈 응답 확인, LLM 접속 및 Tool 선택, 대표 요청의 인자 추적과 재계획 시험이다. 현황은 [API 검증](api_verification.md)에 기록했다.
- 최종 제출은 §4·§6에 따른 요구사항, Agent 설계, Tool 정의, API 명세, 소스, README, 실행 결과 화면 및 로그, 검증 기록, 3일차 체크리스트를 포함한다. 대표 요청 5개 이상에 정상·재계획·상한·Tool 실패·Tool 불필요를 포함하고, 응답/로그/기대와 실제의 차이를 남긴다. 전체 실행 로그 1건과 재계획 사례를 포함해 README로 정리하고 명세서에 지정된 SSAFY Git 서버로 제출한다.

## 프로젝트 자체 설계

TripMind AI는 전국 시도와 시·군·구를 지원하는 국내 여행 일정 플래너다. 초기 검증 사례로 경주를 사용했다. TourAPI 행정구역 코드로 관광지를 찾고 Open-Meteo로 확인된 장소 인근의 강수와 기온을 조회하며, 에어코리아에서 해당 시도의 현재 대기질 참고 정보를 가져온다. 결과물은 날짜와 시간대가 있는 방문 계획이다. 같은 날짜에 겹치는 계획은 저장하고 충돌 목록을 반환한다. 여행 일정 추천 범위에서 건강 관련 판단은 수행 범위에서 제외한다. 제공 API 3종의 확보 여부는 검증 문서를 따른다.

### 대표 사용자 요청

아래는 설계 시험의 기대 경로다. 날짜 해석 기준일은 2026-11-18 KST다. 운영시간, 입장료, 이동시간 및 방문일 대기질은 근거가 있는 경우에만 제시한다.

#### A · 정상 일정 생성

- **요청** — 11월 21일 경주로 당일치기 여행을 가려고 해. 오전 10시부터 오후 6시까지 관광지 3곳을 추천해 줘.
- **의도** — 일정 생성
- **기준·선호·제약** — 11/21 10:00~18:00 · 경주 · 서로 다른 3곳
- **Tool과 호출 순서** — 검색 → 후보 ID별 상세 → 날씨. 대기질 현재 참고를 요청했으면 에어코리아 추가
- **데이터** — ID, 제목, 주소, 좌표, 방문일, 강수 확률, 기온
- **판단** — 서로 다른 후보 3곳, 시간 창 480분. 소요·이동시간 미확인 시 480분 내 충족 여부를 미확인으로 표시
- **재계획** — 적합 후보가 부족하고 새 페이지나 검색 유형이 남아 있을 때
- **응답** — 장소 및 주소, 추천 순서, 소요시간 예산, 판단 근거와 확인 필요 항목, 제외 사유
- **LLM 단독 응답의 문제** — 장소 주소·공간 관계나 실제 운영시간을 잘못 제시할 수 있다

#### B · 비가 올 때 재계획

- **요청** — 11월 21일 경주를 여행할 건데, 비가 온다면 야외 관광지를 실내 관광지로 변경해 줘.
- **의도** — 날씨에 따른 후보 교체
- **기준·선호·제약** — 11/21 · 경주 · 강수 위험 시 실내. 독립 요청이면 운영시간을 적용한 방문 슬롯은 추가 확인 필요
- **Tool과 호출 순서** — 기존 후보와 상세 재사용 또는 검색 → 상세. 날씨 확인 → 위험이면 유형 14로 검색 → 새 ID 상세
- **데이터** — 기존 후보 ID, 실내 근거, 일별 최대 강수 확률, 대체 후보 ID
- **판단** — 일별 최대 강수 확률이 사용자 상한 또는 서비스 기본 50% 이상이면 실내로 교체. `14`는 검색 필터이고 실내 여부는 확인 가능한 근거로 판단
- **재계획** — 야외 후보가 포함되고 강수 기준에 도달하거나, 실내 후보가 부족해 새 탐색이 필요할 때. 강수 결측 시 조건 판단 보류
- **응답** — 강수 기준과 출처, 교체 목록 및 근거, 필요한 경우 일정 시간 질문
- **LLM 단독 응답의 문제** — 여행일 강수 확률이나 장소의 실내 여부를 잘못 제시할 수 있다

#### C · 정보 부족

- **요청** — 이번에 경주로 여행 가려고 하는데 일정 짜 줘.
- **의도** — 일정 생성
- **기준·선호·제약** — 날짜·시각 미정 · 경주 · 수량 미정
- **Tool과 호출 순서** — 날짜, 시간대, 장소 수 질문. Tool 호출 0회
- **데이터** — 사용자 답변의 날짜, 시작·종료, 장소 수
- **판단** — 필수 기준값 입력 검사
- **재계획** — 추가 질문 우선
- **응답** — 여행 날짜, 가능한 시작·종료 시간, 희망 장소 수 질문
- **LLM 단독 응답의 문제** — 누락 조건을 채워 넣으면 사용자가 갈 수 없는 일정이 된다

§2.1의 도구 비교 요청 3건과 §4.7의 실행 유형을 모두 확보하기 위해 세 사례를 추가했다. 구현 후 실행 결과는 [필수 기능 검증](verification.md)에 기록했다.

#### D · 상한

- **비교와 Tool 순서** — “11/21 경주 14~15시, 실내 문화시설 5곳에 각 10분 이상, 이동은 구간당 3분 이내.” 검색 → 상세 → 수량, 실내 근거, 최소 체류 50분 및 이동 예산 10분 비교. 출처상 판정 가능한 대안이 부족할 때 다른 페이지 후보 탐색
- **기대 결과 및 LLM 단독 응답의 문제** — 신규 탐색이 계속 가능한 시험 조건에서 재계획 3회 후 중단. 후보·이동시간을 지어내지 않고 확보된 수, 미확인 사유와 시간 조정을 제시

#### E · Tool 실패

- **비교와 Tool 순서** — “11/21 경주 10~18시, 실내 2곳과 당시 강수 확률을 알려줘.” 검색 → 상세 → 날씨. 검증용으로 날씨 TIMEOUT을 유도
- **기대 결과 및 LLM 단독 응답의 문제** — 관광지 확인은 계속하고 예보는 미확인으로 표시. 가짜 예보로 조건 충족 여부를 만들지 않는다

#### F · Tool 불필요

- **비교와 Tool 순서** — “저장한 여행 일정은 어떻게 지워?” 사용법 안내, Tool 0회
- **기대 결과 및 LLM 단독 응답의 문제** — 계획 관리 화면에서 삭제하는 방법 안내. 요청이 가리키는 실제 계획 ID를 지어내거나 삭제하지 않는다
